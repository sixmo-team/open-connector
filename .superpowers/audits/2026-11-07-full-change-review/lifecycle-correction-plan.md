## Ruling after independent contrasting reviews

Both reviewers withdrew blanket processing-reset/replay. OO provider revocation occurs before its durable outcome marker; a sequential replay test does not prove concurrent single-effect dispatch. Native callback processing must not be reset on observed row state alone while a paused executor may still perform I/O. A separate recovery URL adds no proof: use existing authenticated entry points for clean takeover. Existing dispatcher reuse is allowed; no new timer, job store, lease-age death guess or manual force-unlock.

## Architecture and ownership

Keep app.integration_lifecycle_operations as the only intent/progress owner. Add only a frozen, validated RemovalImpact display projection and a nullable durable pendingDispatch marker for cross-transaction connector mutations. The display projection contains redacted connection/member labels and counts, not action grants and not an executable permission copy. Existing native per-connection processing remains the native dispatch marker.

Keep public DELETE result {status,correlationId}; the canonical stored correlation, not an incoming retry UUID, must be returned and audited. Introduce an explicit internal admission result (admitted/pending/completed plus operation), rather than returning a foreign execution claim as if acquired. No dependency or database-schema upgrade is needed: installed PostgreSQL row locks, JSONB and existing execution-ID CAS provide the needed semantics.
