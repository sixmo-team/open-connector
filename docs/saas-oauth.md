# Scoped managed OAuth connections

The native managed client keeps third-party access/refresh tokens, OAuth app secrets and provider secrets on the external SaaS. OpenConnector stores the project key through OpenBao, durable scoped request/account references in PostgreSQL, and safe metadata. Inputs and outputs travel through that actual remote service. Managed projects and Marketplace API keys are separate configurations; neither enables an OpenConnector function automatically.

## Scope and source selection

Configure the actual workspace project and selected provider source through the operator-only **Managed project** page in the existing protected console. The backend gateway forwards the six [private controls](contracts/saas-runtime.openapi.yaml): project read/configure/remove, provider-configuration discovery and provider-source read/select. Selection requires the actual tenant and workspace, not a customer user. A distinct short-lived signed `configuration:read` or `configuration:write` capability carries the verified operator and exact workspace; writes bind the original method/path/target/body. The gateway has no customer execution key and stores no project key or duplicate configuration.

OpenConnector alone validates discovery, owns the workspace rows and stores the key in OpenBao. Keys and secret references are never returned, written to browser storage or included in the operator audit. The original issuance timestamp precedes the backend workspace-authority query, so a delayed successful lookup cannot renew authority after a removal fence. There is no global project, public console settings page, static administrator token, public connector callback or default connection fallback. Key replacement retains the established origin/project; deletion refuses active source/account/request/cleanup references. Failed secret erasure retains metadata for a retry that does not require decrypting an already-erased key.

A project-key write reserves its exact scoped secret reference durably before dispatch. Initial pending or retired-only custody is not an active configuration; the real cleanup-paused state remains visible without invented queue counts. A pending write blocks replacement and both optional and lifecycle removal. Confirmed key creation with failed publication retains the exact reference for guarded cleanup, never silently activates an orphan. An indeterminate original OpenBao write stays fenced: a timeout, a missing current value, a replayed compare-and-set or process death does not exclude a late write. Resolve only from an authoritative original-owner outcome; do not erase custody to hide the failure.

Both removal paths commit an inactive project before erasing a settled key: the active reference moves to retired custody, `secret_ref` becomes null and cleanup remains paused. A failed or partial erase cannot roll the project back into use. New source and managed-request references share-lock the exact active project through publication; a previously captured key cannot create a new dependency after that fence. A guarded retry completes the same inactive reference snapshot without decrypting an erased key. Replacement remains blocked until removal finishes.

Provider-source discovery is submitted explicitly rather than requested for each typed prefix. Switching workspaces remounts the page and clears typed secrets and obsolete responses. These management controls do not enable product admission, action permissions or customer execution; existing backend roles, billing and command consent remain unchanged.

New managed authorization uses the selected workspace project/provider configuration. Existing connections retain their captured local/custom/managed source on reconnect; selecting a managed workspace default must not move an existing local connection. Managed authorization rejects request-level client/scope/secret overrides; configure these at the actual remote provider configuration. Local custom-client admission remains explicitly restricted.

A trusted deployment-supplied managed completion URI (`OOMOL_CONNECT_MANAGED_COMPLETION_URI`) and the working backend continuation handler are required. The scoped wrapper binds start/poll/cancel/completion to the original verified session, owner and local connection lineage. Poll a known request, respect Retry-After, and complete the original attempt; never start another authorization merely because a response was lost. A mismatched project/config/external-user/account/alias is not adopted. The remote external-user selector is deterministically tied to the genuine tenant/workspace/local lineage, not a process-global instance or fabricated user.

## Readiness and execution

Selected managed readiness uses current scoped source/project/key discovery rather than a startup snapshot or a local-app fallback. Missing/malformed/rejected configuration is distinct from a database, OpenBao or vendor outage. Do not label an unavailable source as operational or erase its saved selection.

The backend reads this through `GET /internal/saas/catalog/providers/scoped` with a verified `connection:read` capability and actor equal to subject. No query or caller-selected identity is accepted. It returns the same safe provider catalog schema as `/internal/saas/catalog/providers`, including `no_auth` methods, `status` and bounded OAuth `reasonCode`; the unscoped `catalog:read` endpoint reports local application readiness only. A scoped discovery/storage outage returns `503 catalog_unavailable`, not a fabricated readiness result. Neither catalog endpoint enables product admission or action permission.

Managed request reads use `GET /internal/saas/oauth/requests/{requestId}`; cancellation uses `POST /internal/saas/oauth/requests/{requestId}/cancel` with exactly `{}`. Both require the original `oauth:complete` capability's interactive actor, owner, local connection and session lineage. They return only safe request state and, after verified completion, safe connection metadata; knowing a request UUID is insufficient authority.

The scoped action runner checks the original actor's current OpenConnector rule, exact signed action/input/connection and active owner/visibility before native managed execution. The adapter rereads every stored account selector and actual source binding. Only the intersection of local catalog and current remote capability is executable. The remote transport retains safe errors, Retry-After and remote execution IDs; it does not expose a public arbitrary proxy.

Cancellation and the inherited connector processing deadline bound local waiting/vendor work. A timeout, lost response or caller abort does not prove a remote mutation failed and never authorizes automatic replay, switching accounts, or local fallback. Inspect the real remote execution/provider resource first. Remote billing/credits remain the vendor's responsibility; OpenConnector does not fabricate balances or new spending caps.

## Unknown results and recovery

Retain known local request/account references through cleanup. If vendor retention has expired or identity is uncertain, require operator investigation rather than reporting successful deletion. Compare the real bound project, provider configuration, external-user selector, exact request/account ID and attempt alias; an email/display name alone is insufficient. Restore references from a verified backup when needed. Do not reset storage to hide an outage.

Switching to local OAuth is explicit: preserve the old managed row/cleanup, provision the real scoped local client, create a new connection with a distinct alias, authorize/verify its account/scopes, and update exact backend selectors after policy checks. Reconnecting the existing managed row still uses its original source. See [scoped cleanup](saas-maintenance.md) and [deployment recovery](saas-deployment.md). Actual vendor consent, continuation, credit/error behavior and infrastructure require live qualification; source code or protocol fixtures do not establish that qualification.
