# Scoped managed-account cleanup

Managed account cleanup belongs to the same verified tenant/workspace/owner/local lineage as the connection, original request and project key. Native remote deletion uses the exact provider configuration, external user and account selector; it does not borrow a neighbor's project key or revoke a local provider token as a substitute.

Deleting/replacing a connection must retain the genuine old remote account/request reference as durable cleanup work. If only a request ID is known, resolve and validate that exact request before adopting an account selector. Unknown creation outcomes and expired/unverifiable vendor results require manual attention, not fabricated success or another authorization attempt. A crash after successful remote deletion can require repeating the same idempotent deletion; it must not erase the stored account selector first.

Cleanup is invoked through the authenticated scoped service/lifecycle boundary and inherits its original cancellation/deadline. There is no autonomous process-global token scheduler, Worker cron, D1/SQLite reset command or second maintenance listener in this branch. Never retain a SQL client/transaction across remote HTTP work that needs independent scoped transactions. Keep clocks synchronized for actual persisted leases and retry times; Retry-After does not extend the root processing budget.

The same authenticated actor-bound maintenance pass also erases at most 100 expired transit files through the existing native file service. PostgreSQL metadata selects only the verified actor's files in the current tenant/workspace, including files produced with a shared credential; the credential owner's files, other actors and live files are not swept. Object-store deletion precedes metadata removal. A failed deletion retains durable reconciliation metadata and fails the pass rather than reporting HTTP 204; cancellation retains the original processing budget and unresolved metadata for a later pass. No global object scan or separate timer is introduced.

Project/key rejection, network/storage outage, uncertain remote writes and failed secret deletion retain genuine retry/reconciliation state. A source/configuration deletion must not erase unresolved account cleanup. When manual work is required, inspect the exact bound project/configuration/external-user/request/account IDs and recorded outcome. Only verified-unused accounts may be removed; a matching email or display name is not ownership proof. Record the actual remote result before resolving the matching task. Never clear pending work, disable RLS, fabricate an owner or reset a database to conceal failed cleanup.

## Native private-envelope custody

Trigger subscriptions, persistent Source state, connection requests and managed candidates use one native `secret_custody` owner. Each immutable allocated reference is committed as `pending` before the original OpenBao write; SQL contains only exact scope, owner, actor/credential lineage and target metadata, never the payload. After the original write succeeds, owner publication and consumption of that pending row commit together. A known-written publication loser first commits `deleting` on the same row, then erases outside SQL. This ordering prevents a delayed publication from installing an already-erased envelope.

Unknown original writes stay `pending` and block subject purge even if no parent row was published. A current 404, a readable value, timeout, cancellation, process death or compare-and-set replay does not prove that the original write cannot arrive later. Only the original invocation's authoritative outcome may release that custody. There is no automatic inference of success, permanent native user tombstone or copied backend membership state.

Terminal and purge operations commit a no-read/no-publish owner fence and settled references in `deleting` custody before external erasure. Local requests use the internal `purging` phase; completed managed requests retain their return URI until the existing retention boundary. Failed erasure preserves deleting custody for a safe retry and cannot restore a readable owner. Native lifecycle `requestSecrets` counts real attached and detached request references separately from request metadata; empty parent metadata is not an empty secret inventory.

The existing actor-bound maintenance pass drains only settled `deleting` references, including detached Trigger envelopes, with the original cancellation and deadline. Pending/unknown references and other actors, workspaces and tenants are not swept. Account/provider cleanup and transit-file maintenance keep their existing owners and checks.

Migration `0019_scoped_secret_custody.sql` is a controlled cutover: stop the old runtime and authoritatively reconcile every old `trigger_secret_cleanup` row first. Those old rows do not establish original outcomes or actor/credential lineage. The migration refuses a nonempty queue without dropping its data; it neither guesses ownership nor treats absence as settlement. Deploy the matching native runtime and strict backend wire contract together; do not replace missing `requestSecrets` with zero.

There is deliberately no general-purpose offline clone/reset CLI. Use the existing [backup, restore, migration and rollback runbook](saas-deployment.md), isolate restored test infrastructure and secrets, and prevent a verification clone from deleting production vendor accounts. A rendered chart, migration ledger or protocol fixture is not proof of vendor deletion or successful recovery.
