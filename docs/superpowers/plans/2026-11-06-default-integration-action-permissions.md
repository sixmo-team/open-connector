# Общие разрешения действий OpenConnector — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Один раз настраивать общие разрешения действий в OpenConnector, поддерживать индивидуальные исключения и существующие пакетные операции, не смешивая ответственность с сервером ИИ-маркетолога.

**Architecture:** OpenConnector хранит, рассчитывает и окончательно проверяет индивидуальные и общие разрешения действий. Сервер ИИ-маркетолога сохраняет пользователей, членство, роли, тарифы, допуск интеграций в продукт, проверенную классификацию безопасности и подтверждения; решение OpenConnector получает по защищённому сетевому договору, не рассчитывая наследование сам. Сервисы используют собственные базы и настройки адресов; наличие общей машины, процесса, файлов или доступа к чужой базе не требуется.

**Tech Stack:** Существующие TypeScript, PostgreSQL, Hono, React, Vitest и подписанные короткоживущие запросы; без новых библиотек или отдельной системы пользователей.

**Spec:** [Platform action defaults](2026-08-04-native-multitenant-integration-runtime.md#platform-action-defaults).

**Status:** Реализация выполнена на изолированных ветках: разрешения перенесены в OpenConnector, общие правила и индивидуальные исключения используют существующую пакетную панель; роли, тарифы и согласие человека переиспользуются в бекенде. Реальных пользователей нет: прежние тестовые разрешения не импортируются и вторая рабочая копия правил не поддерживается. Окончательная квалификация отдельных сервисов, образа и панели относится к внешнему отчёту неизменяемого кандидата; производственное развёртывание не выполнено. Раздел «Проверенная исходная точка» ниже описывает состояние до реализации, а не текущего владельца данных.

**Существующее поведение, не новая задача:** роли, тарифные ограничения и пользовательские подтверждения уже реализованы в бекенде ИИ-маркетолога. Их код и обычный порядок работы переиспользуются. Меняются владение разрешениями функций и необходимая связь с OpenConnector; отдельного проекта реализации ролей, тарифов или подтверждений нет. Разделение хранилища дополнительного `always` не создаёт второй процесс получения согласия.

Пути в `Files` указаны относительно корня OpenConnector. Соседние пути нужны разработчику при изменении договоров, но не являются зависимостью работающих сервисов. Тяжёлые проверки выполнять последовательно.

**Актуальная рамка:** [Границы сервисов и инкапсуляция](../specs/2026-11-06-service-boundaries-and-upstream-sync-design.md). OpenConnector и бекенд ИИ-маркетолога — отдельные программные сервисы на одной физической машине; местоположение панели не определяет владельца настроек. При [обновлении main → multitenant](2026-11-06-upstream-main-multitenant-sync.md) сохранить эти требования, но не объявлять данный план выполненным по самому факту слияния.

## Global Constraints

- Общие и индивидуальные разрешения действий хранятся, рассчитываются и проверяются только OpenConnector.
- Пользователи, членство, роли, тарифы, допуск интеграций в продукт и подтверждения остаются ответственностью бекенда ИИ-маркетолога.
- Рабочий обмен сервисов идёт через защищённые настраиваемые сетевые адреса; чужие базы, общие файлы и соседний каталог репозитория не являются зависимостями.
- Реальных пользователей нет: старые тестовые настройки не переносятся; полезные возможности и проверки безопасности сохраняются.
- Индивидуальное исключение для конкретного действия пользователя в пространстве имеет приоритет над общим правилом.
- Если нет явно включённого индивидуального или общего правила, действие запрещено.
- Существующие таблица, фильтр интеграции и пакетные операции панели переиспользуются; пакет не превращается в цикл отдельных сетевых запросов.
- Новые действия не включаются по маске или автоматически при обновлении каталога.
- Административный доступ к настройкам не даёт права выполнять действия с клиентскими подключениями.
- Сбой OpenConnector или чтения его правил не заменяется локальными разрешениями сервера ИИ-маркетолога.
- После переключения нет двух рабочих источников разрешений или старой совместимости; общие правила не копируются в каждого пользователя.
- Меняются только планы и, при отдельной реализации, пути OpenConnector; код остальных интеграций не затрагивается.

## Подтверждение пользователя — не разрешение функции

В текущем коде одна строка содержит два разных факта: `enabled` разрешает действие для пользователя в пространстве, `approval_override` может потребовать его отдельного согласия на конкретную команду помощника.

- `inherit` означает обычное требование согласия из проверенной классификации безопасности; оно не наследует разрешение функции.
- `always` дополнительно требует согласия даже там, где обычное правило его не требует. Этот флаг не может отключить обязательное подтверждение или разрешить запрещённую функцию.
- Действующий `IntegrationActionPolicy` сначала запрещает отсутствие `enabled` (`action-policy.ts:93-95`), отдельно рассчитывает `requiresApproval` (`:119-123`). `validateApproval` проверяет согласие на точные действие, подключение и аргументы (`action-execution-service.ts:347-359`).

После переключения OpenConnector единолично проверяет **разрешение функции**. Бекенд ИИ-маркетолога единолично проверяет **согласие человека на команду**, свои роли и тариф. Положительный ответ одного не заменяет положительного ответа другого. Отдельная таблица дополнительных требований согласия в бекенде ИИ-маркетолога не содержит `enabled`, общих разрешений или копий правил OpenConnector. Её новые записи нужны только для дополнительного `always`; отсутствие записи оставляет обязательную базовую безопасность.

## Целевой порядок действий

```text
Панель: существующая таблица и пакетное включение/отключение
  -> защищённый шлюз: проверка оператора и точной цели
  -> сетевой метод OpenConnector: проверка команды и одна транзакция правил/аудита

Бекенд ИИ-маркетолога: проверка пользователя, роли, тарифа и допуска интеграции
  -> пакетный ответ OpenConnector о разрешениях инициатора
  -> существующий ограниченный поиск инструментов
  -> повторная проверка бизнес-доступа и ответ OpenConnector перед запросом
  -> подписанное исполнение action:execute:v2 для точного подключения и содержимого
  -> OpenConnector заново проверяет собственное правило до повтора/исполнения
  -> существующий исполнитель поставщика
```

Полный каталог и поиск описаний остаются справочником, а не доказательством права. Для разрешённого набора используется отдельный пакетный ответ OpenConnector; нельзя менять отпечаток служебного каталога под пользователя или строить второй поисковик.

Подключение аккаунта не выдаёт права на его действия. Общие разрешения не делают личное подключение общим. Общий запрет не отменяет индивидуального разрешения: принудительное выключение интеграции для продукта относится к отдельной конфигурации сервера ИИ-маркетолога.
